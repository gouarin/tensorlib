# Thin templates over an erased core, and layered extension points

Every public operation is a template constrained by the `tl::operand` concept, and its body is one line: it turns its operands into erased expressions with `tl::as_expr` and calls a non-template function compiled once in a `.cpp`, which records the node. `fixed<T, N...>` is the only substantial generic code in public headers. Users extend the library through three mechanisms, chosen by what they add. Element types are described by specialising `tl::element_traits`, checked by the `tl::element` concept. Run-time behaviour (backends, memory resources, library operations, external functions) is registered at run time behind type-erased interfaces. New operations are compositions: plain functions on `tl::expr`, or traced functions. The IR's primitives are closed to users; a scalar function that cannot be composed is registered as an external function and reached through a single `call` operation, with a host symbol and optional LLVM bitcode per target.

We rejected expression templates and other generic bodies in headers, because [Prototype of compile times for lighter templates](../../.scratch/core-architecture/issues/11-compile-time-prototype.md) measured 37 to 127 s of compilation for xtensor where a recording front-end takes under half a second, and the gap grows with code size. We rejected customisation point objects found by ADL and `tag_invoke`: once types are erased behind `tl::expr`, they add lookup rules and long diagnostics while giving almost nothing over a trait, and `std::execution` moved away from `tag_invoke` for the same reasons. We rejected member functions on `tensor` for operations (`a.sum()`), because users cannot add members, so their operations would read differently from the core's, and every member weighs on every translation unit. We rejected an open registry of IR primitives with user lowerings, because it would make the IR builder and a pinned LLVM version part of the public API and require one lowering per target from each user.

## Consequences

- Each core operation has two parts, a one-line facade and a compiled body. CI checks the facade rule, the header whitelist, and the absence of C++23 conditional paths in public headers.
- An operation written by a user looks and behaves like a core one: same free-function form, same operands, same fusion.
- An external function without bitcode for a GPU target cannot run there; building the plan raises `tl::unsupported_operation`. On CPU, a call that is not inlined still fuses but is not vectorised.
- Results that depend on an external function are only as reproducible as that function.
- A real new primitive still needs a change to tensorlib: an IR node, its lowering per target, and its serial interpreter.
