# Code-generation strategy

Type: grilling
Status: resolved
Blocked by: 02, 03, 11, 16

## Question

Which code-generation strategy does the core use: lighter templates, a run-time graph compiled by a JIT, or both, and where is the boundary between them (for example templates for fixed-shape tensors)? It must also say how a graph that repeats every time step is reused (kernel cache keyed by graph signature, optional capture and replay to skip graph construction), given [When the task graph is evaluated](08-evaluation-trigger.md).

[Prototype of multi-output fusion](09-multi-output-fusion-prototype.md) settled one constraint: whatever the strategy, fused kernels must be straight-line loops. A block interpreter costs 1.2 times the hand-fused loop on DRAM-sized data and 1.5 times on cache-sized data, and it does not map to GPUs, so at best it is a fallback. The copy-on-write uniqueness check costs nothing inside kernels: [Buffer reuse and allocation](21-buffer-reuse-and-allocation.md) runs it on the host, once per buffer and evaluation.

[Prototype of compile times for lighter templates](11-compile-time-prototype.md) settled the template side: expressions on run-time-sized tensors go through a graph-recording front-end with no expression templates, and `fixed<T, N...>` is evaluated eagerly. What remains is how the recorded graph becomes straight-line kernels (JIT through LLVM, NVRTC/hiprtc, precompiled specialisations, or a mix), with the cold-compile cost, the kernel cache, and graph reuse across time steps.

No GPU is available for now (user, 2026-10-30), so this ticket no longer waits for [Rerun the fusion benchmark on an HPC node and a GPU](19-rerun-fusion-benchmark-hpc-gpu.md). Decide on the CPU numbers and the constraints above; the GPU rerun checks the decision later and may reopen it.

## Answer

Decided with the user on 2026-10-30, without GPU numbers: the CPU prototypes and [Feasibility of JIT compilation with Kokkos](03-jit-with-kokkos.md) are the evidence, and [Rerun the fusion benchmark on an HPC node and a GPU](19-rerun-fusion-benchmark-hpc-gpu.md) checks the GPU side later. Vocabulary (evaluation plan, kernel bundle) is in `CONTEXT.md`. The generator choice is recorded in [ADR 0008](../../../docs/adr/0008-in-process-llvm-as-the-only-code-generator.md).

- **Generator.** One generator turns the tensorlib IR into LLVM IR (IRBuilder), compiled by an LLVM linked into the Kokkos backend: ORC on CPU, NVPTX then the driver's PTX JIT on NVIDIA, AMDGPU on AMD, SPIR-V then Level Zero on Intel. Each operation has a small lowering, with a table of intrinsics per target for barriers, shared memory and atomics. Developers read the tensorlib IR printed by `TL_DEBUG=dump`, and the optimised LLVM IR on request. Source strings per vendor, Clang in the process and Proteus as the generator were rejected (see the ADR); Proteus may be reconsidered for GPU loading and caching only.
- **When compiling is not possible.** The JIT is required in the Kokkos backend. Kernels go through a two-level cache (memory, then disk). A kernel bundle (object code, cubin, AMD code object, SPIR-V), produced by a training run or by `tl-aot` from a recorded trace and versioned by the cache key, loads read-only. A kernel missing from the bundle is compiled by default, or is an error under `TL_JIT=off`, for sites that forbid run-time code generation. The serial backend stays the only interpreter; a tiered interpreter in the Kokkos backend was rejected (two performance paths, last-bit differences, no GPU mapping). On Windows, ORC also serves the CPU, with the serial backend as fallback.
- **Cache key.** The structure of the graph, element types and lanes (`fixed<T, N>`), the broadcast pattern (axes with stride 0), stencil shifts, aliasing between operands, the target and its capabilities, one "inner stride is 1" flag per operand, and the versions of the generator, of LLVM and of the options. Extents, offsets, stride values, segment tables and scalars are kernel arguments, so samurai's adaptations and ponio's `dt` and stage coefficients never recompile. Scalars are arguments because C++ cannot tell `2*b` from `dt*b`; `tl::constant(2.0)` puts a value into the key on purpose. Alignment is handled at run time by a peeled head loop.
- **Reuse across time steps.** An automatic plan cache, keyed by the window's signature (the cache key plus buffer identity and aliasing), stores the evaluation plan: kernels, buffer plan, inserted ghost exchanges, launch configuration. A window seen before skips planning and pays only recording (~5 ns per node) and hashing (under 1 us). Turning a stable plan into a CUDA or HIP graph (`Kokkos::Experimental::Graph`) is an internal backend optimisation, to measure on a GPU. No explicit capture API in v1; it is reopened if a reference benchmark shows recording dominates.
- **Distributed runs.** Every rank compiles what it misses and keeps it in memory: wall time is that of one compilation. On disk, only local rank 0 of each node (shared-memory communicator) writes, through a temporary file and an atomic rename; other ranks only read. The directory is `$XDG_CACHE_HOME/tensorlib` by default, `TL_CACHE_DIR` overrides it, and an unwritable directory falls back to memory only. No collective is needed, so non-collective windows (samurai's local fields) work the same. The disk cache and bundles hold executable code and are documented as trusted. Production jobs ship a bundle.
- **Floating point.** FMA contraction is allowed. Reductions split the iteration space into blocks of a canonical size, independent of thread count and of the machine's SIMD width, reduce each block in a fixed order over canonical lanes, then combine blocks in a fixed tree: results are bit-identical for any thread count on one machine, and reproducible for a fixed number of ranks. Independence from the number of ranks is a later option with a costlier reduction. `TL_FP=strict` turns contraction off for bit equality with the serial oracle; otherwise the oracle compares with a documented tolerance. Fast-math flags on NaN and Inf are never used, so the `nan` check of [Error reporting and debug mode](24-error-reporting-and-debug-mode.md) stays valid.
- **CPU execution.** Kokkos owns the threads. The JIT emits `body(begin, end, args)` over a slice of the iteration space (segments included), and a precompiled trampoline in the Kokkos backend calls it from `Kokkos::parallel_for`, or `parallel_reduce` combining canonical blocks in a fixed order. Slices are multiples of the canonical block. The generator emits a scalar inner loop with `noalias` and loop-vectorize metadata, since the graph knows the aliasing exactly, and explicit vector code only for `fixed` lanes and canonical reductions. Emitting OpenMP runtime calls and ISPC-style fully explicit vectorisation were rejected. On GPU, kernels are launched by the driver on the stream of the Kokkos execution-space instance, with a grid derived from capabilities.
- **Kernel size.** The core splits a fused kernel when it exceeds one of two ceilings from the backend's capabilities: operations per kernel (compile time grows superlinearly) and simultaneously live values (register pressure, spills on GPU). Defaults are per target and tunable (`TL_MAX_KERNEL_OPS`, `TL_MAX_KERNEL_LIVE`). The cut goes where the stored temporary is smallest. The rule is deterministic, part of the plan key and identical on all ranks of a homogeneous job. A cost model can replace it later behind the same splitting interface.
- **Follow-ups.**
  - [Prototype of the LLVM JIT on CPU](27-llvm-jit-cpu-prototype.md) measures cold compile cost, vector code quality and the CPU ceilings, without a GPU.
    It set the first CPU defaults: `TL_MAX_KERNEL_OPS` about 1 000 operations and `TL_MAX_KERNEL_LIVE` 24 lanes on NEON.
  - [Rerun the fusion benchmark on an HPC node and a GPU](19-rerun-fusion-benchmark-hpc-gpu.md) gains the NVPTX and AMDGPU paths, the GPU ceilings and CUDA or HIP graphs.
  - [Kernel IR](22-kernel-ir.md) receives the requirements below.
- **Requirements passed on to [Kernel IR](22-kernel-ir.md):** a canonical, hashable form with arguments separated from structure; a per-operand inner-stride flag; reductions expressed over canonical blocks; a printable text form for `TL_DEBUG=dump`; lowering per operation to LLVM IR with per-target intrinsics; a splitting interface driven by the two ceilings.

Grilling log (2026-10-30):

- Q1 generator: option A. One generator from the tensorlib IR to LLVM IR, in-process LLVM in the Kokkos backend only; Proteus at most for GPU loading and caching.
- Q2 no JIT: option A. JIT required in the Kokkos backend; memory and disk cache; read-only precompiled bundle (tl-aot or training run); TL_JIT=off requires a complete bundle; the serial backend is the only interpreter.
- Q3 cache key: option A. Minimal key (structure, types and lanes, broadcast pattern, stencil shifts, aliasing, target, unit-stride flag, versions); everything else is an argument, scalars included, except tl::constant.
- Q4 reuse: option B. Automatic plan cache keyed by the window signature; CUDA/HIP graphs as an internal backend optimisation; no explicit capture in v1.
- Q5 distributed cache: option A. Every rank compiles, local rank 0 per node writes with an atomic rename, configurable directory, memory fallback.
- Q6 floating point: option B. FMA allowed, reductions in a fixed order over canonical blocks, reproducible for a fixed rank count; TL_FP=strict; no fast-math on NaN and Inf.
- Q7 CPU execution: option A. Kokkos owns the threads, the JIT provides body(begin, end, args), vectorisation through LLVM noalias and loop metadata, explicit vectors only for fixed lanes and canonical reductions.
- Q8 kernel size: option B. Two tunable ceilings from capabilities (ops, live values), deterministic cut at the smallest temporary, splitting interface open to a cost model.

## Comments
