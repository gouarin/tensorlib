# Coding style and extension points

Type: grilling
Status: resolved

## Question

The Notes set a quality bar for the code written from this spec. It has to be very easy to read, concise, modern C++, and very flexible. Decide the rules that get it there, within the C++20 floor and the light-header budget of [Minimum C++ standard and build system](14-cxx-standard-and-build.md) and the recording front-end of [Prototype of compile times for lighter templates](11-compile-time-prototype.md):

- language features the code relies on: concepts and `requires` clauses in place of SFINAE, designated initializers for option structs, `std::span`, `<ranges>` only in `.cpp` files, and which C++23 features (deducing this, `std::expected`) get an optional path behind feature-test macros;
- how users and later efforts extend the library without editing the core: new element types, new operations and combiners, new library operations, new backends and memory resources. Candidates are trait specialisation, customisation point objects, `tag_invoke`, and the run-time registries already decided for backends. Each must be weighed against compile time and header weight;
- naming and layout: namespaces (`tl::`, `tl::detail`, one per backend), file and header layout, what goes in headers and what goes in `.cpp`, naming conventions;
- local rules: `[[nodiscard]]`, `noexcept`, `const`, `constexpr`, ownership in signatures, and when to use a class or a free function;
- how readability and conciseness are enforced: clang-format and clang-tidy profiles, CI checks, a review checklist, and examples that compile as tests.

The answer is the list of style rules that the spec must state before it is split into implementation tickets.

## Answer

Decided with the user on 2026-10-31. The extension model and the header rule are recorded in [ADR 0011](../../../docs/adr/0011-thin-templates-over-an-erased-core-and-layered-extension-points.md). Operand and external function are in `CONTEXT.md`.

- **Extension points.** Each kind of extension gets the simplest mechanism that covers it:
  - element types are described by specialising `tl::element_traits`, checked by the `tl::element` concept;
  - run-time behaviour (backends, memory resources, library operations) goes through run-time registries behind type-erased interfaces, as in [ADR 0003](../../../docs/adr/0003-runtime-backend-interface-on-lowered-kernels.md);
  - new operations are compositions: plain functions on `tl::expr`, or traced functions.

  The public API has no customisation point objects and no `tag_invoke`.
- **External functions.** The core IR primitives stay closed to users. One IR operation, `call`, invokes a registered external function. Its registration gives a host symbol, which is required and serves the serial interpreter and the CPU, and optional LLVM bitcode per target (CMake helper `tl_add_device_function`). The generator inlines the bitcode when it exists and calls the host symbol on CPU otherwise. On a GPU without bitcode, building the plan raises `tl::unsupported_operation`. The bitcode hash enters the kernel cache key. Neither LLVM nor the IR builder is part of the public API.
- **Call style.** Operations are free functions only, with Array API names and semantics. Options go in a small aggregate per function family, passed with designated initializers: `tl::sum(a, {.axis = 0, .keepdims = true})`. There is one form per call, and adding an option never breaks existing calls. `tensor` members are limited to intrinsic properties (`shape()`, `dtype()`, `distribution()`), `operator()` for views, and assignment. There are no convenience members such as `a.sum()`.
- **Thin templates, erased bodies.** A public operation is a template constrained by `tl::operand` whose body is one line. That line normalises the operands with `tl::as_expr` and calls a non-template function compiled once in a `.cpp`, which records the node on an erased expression. `fixed<T, N...>` is the only substantial generic code allowed in public headers. Users may write fixed-type functions on `tl::expr<T>`, or generic ones constrained by `tl::operand`; the documentation shows both.
- **Names.** `snake_case` for types, functions and concepts; `PascalCase` for template parameters; no member prefixes; a `_options` suffix for option aggregates. `tl` holds the public API, `tl::detail` the internals, and each optional component has its own namespace (`tl::kokkos`, `tl::serial`, `tl::mpi`, `tl::petsc`, `tl::tpetra`). There is no inline versioned namespace, because binary stability lives in the C ABI. Macros and environment variables take the `TL_` prefix, and the API has no macros except C++23 feature tests.
- **Layout.** Public headers live in `include/tl/` and internal ones in `include/tl/detail/`. `src/<component>/` mirrors that tree, and each file holds one glossary concept and is named after it. Users include one umbrella header, `<tl/tl.hpp>`, plus one header per optional component (`<tl/kokkos.hpp>`, `<tl/petsc.hpp>`...). Fine-grained headers exist only under `tl/detail` and are not part of the API.
- **C++23.** Public headers are strict C++20, with no conditional paths. C++23 enters the API all at once, replacing the C++20 code, when the floor moves. The library's own `.cpp` files build as C++20 at first. Their standard can be raised separately once the whole host toolchain allows it, never by keeping two versions of the code.
- **Local rules.**
  - Functions observe by `const&` and take what they keep by value, then move it. Raw pointers never own. Smart pointers stay internal. Small host lists are `std::span` or `std::initializer_list`.
  - `noexcept` follows the Lakos rule: accessors, moves and `swap` only, never an operation that records a node, since it may throw `tl::shape_error`.
  - `fixed<T, N...>` and the arithmetic of shapes, indices and type promotion are `constexpr`, and their tests are `static_assert`s.
  - A class exists only to protect an invariant. Data without one is a plain aggregate (options, `tl::box`, `tl::site`), and behaviour lives in free functions. The only public inheritance is in exceptions and in the pure abstract registry interfaces.
  - Local variables are `const` when they do not change.
  - `[[nodiscard]]` sits on the types `expr`, `tensor` and `view`, so every function returning them warns when the result is dropped. A function gets the attribute only when it returns another type and dropping it is a bug.
- **Enforcement.**
  - clang-format and a curated clang-tidy profile (`modernize`, `readability`, `bugprone`, `performance`, part of `cppcoreguidelines`, a cognitive-complexity threshold).
  - Strict warnings (`-Wall -Wextra -Wpedantic -Wconversion -Wshadow`, `/W4`), errors in CI only and never imposed on installed targets.
  - CI scripts check the header whitelist of [Minimum C++ standard and build system](14-cxx-standard-and-build.md), the absence of C++23 conditional paths in public headers, and the one-line facade rule.
  - Every public function has a documentation example that CI compiles and runs on the serial backend.
  - `CONTRIBUTING.md` holds a short review checklist for what no tool checks: names come from the glossary, there is one way to write each thing, extensions use the mechanisms above, and a function reads without opening its `.cpp`.
  - The choice of tools goes to [Test and benchmark infrastructure](32-test-and-benchmark-infrastructure.md).
- **Amendments.** [Kernel IR](22-kernel-ir.md) gains the `call` operation. [Minimum C++ standard and build system](14-cxx-standard-and-build.md) no longer allows optional C++23 paths in public headers.
