# Buffer reuse and allocation

Type: grilling
Status: resolved
Blocked by: 20, 10

## Question

How does tensorlib get storage for evaluated tensors and kernel temporaries? Decide when an evaluation writes in place into the old buffer of a uniquely held handle (the copy-on-write uniqueness check, validated in [Prototype of multi-output fusion](09-multi-output-fusion-prototype.md)), which pool backs new allocations (from [Memory pools for HPC tensors](20-memory-pools-research.md)), how temporaries between split kernels are planned and freed, and how stream-ordered frees work with asynchronous evaluation. The answer sits behind the [Backend interface](10-backend-interface.md).

Requirements from [Reconcile the core with samurai and ponio](26-reconcile-with-samurai-ponio.md): cheap reallocation at a new size at every adaptation step, staggered start offsets for large buffers (ponio PR #115 lost up to 43 % to page-aligned arrays), and in-place reuse of the output of ponio's `f(t, y, dy)` when `dy` is uniquely held.

Requirements from [Zero-copy interop with PETSc and Tpetra](17-petsc-tpetra-interop.md): packing buffers for `borrow_packed`, outputs of PETSc and Tpetra operator nodes, and the host side of Tpetra `DualView`s (allocated only on host access) all come from the pool.

## Answer

Decided with the user on 2026-10-30. Vocabulary (memory resource, capacity) is in `CONTEXT.md`. The resource interface and the Umpire dependency are recorded in [ADR 0005](../../../docs/adr/0005-queue-ordered-memory-resources-with-umpire.md).

- **In-place reuse.** Only the target of an assignment takes back its old buffer. The core checks uniqueness on the host when the window is evaluated, with window nodes counted as references, once per buffer. Generated kernels never check anything, so the copy-on-write test costs nothing inside a kernel. A buffer has a capacity: the target is reused when the new size fits and fills at least half of it, otherwise the buffer goes back to the pool. This covers ponio's `f(t, y, dy)` with a uniquely held `dy` and samurai's fields, whose size moves a little at every adaptation. Donating the buffers of dying operands (as JAX does) is left out until a reference benchmark asks for it.
- **Umpire is required by the Kokkos backend.** The serial backend keeps aligned `operator new`, since it is not a performance target. There is no home-grown fallback pool. This amends [Backend interface](10-backend-interface.md), which made Umpire optional.
- **Memory resources.** Each memory space has one type-erased `tl::memory_resource`, with `allocate(bytes, alignment, queue)` and `deallocate(ptr, bytes, alignment, queue)`, ordered by queue like the CCCL `cuda::mr` concept. The default is an Umpire pool. `tl::umpire_resource(umpire::Allocator)` ships with the Kokkos backend, and `tl::cccl_resource` and `tl::rmm_resource` live in optional headers, so an application can share its own pool with tensorlib. `tl::set_resource(space, r)` must run before the first allocation in that space; changing it later is an error.
- **Frees in queue order.** When a buffer dies, the core makes the queue of its last access wait on the buffer's other pending events, then calls `deallocate(..., queue)`. The host never blocks, and memory is reusable at once on that queue. The default pool is Umpire's `ResourceAwarePool` from v1, because `tl::on(queue)` already allows several queues. A resource that is not queue-ordered says so, and the core keeps its frees in a `(ptr, event)` list polled at each allocation and evaluation.
- **Temporaries between split kernels.** In v1, the planner allocates each temporary from the resource at its first writer and deallocates it right after its last reader is enqueued, so the pool recycles memory between temporaries of one window. The logical peak of live bytes feeds the planned-bytes trigger of [ADR 0002](../../../docs/adr/0002-implicit-pending-windows.md), never the pool state. A per-window arena with offsets planned once (XLA buffer assignment) can replace this behind the same planner interface if the CI budget on the fixed cost of an evaluation shows the pool calls matter. Workspaces of library operations come from the same resource when the library accepts one.
- **Staggered start offsets.** A `tl::staggered(resource)` adaptor wraps the host resources by default. Above 64 KiB it asks for 4 KiB more and shifts the start by `(i x 64 B) mod 4 KiB`, with a rotating counter per space, keeping 64 B alignment. Cache line, page size and required alignment come from backend capabilities. It is off for device spaces until [Rerun the fusion benchmark on an HPC node and a GPU](19-rerun-fusion-benchmark-hpc-gpu.md) shows a gain. Acceptance test: ponio `heat_bench` with `rkc_202` on 10^6 cells, which lost 43 % to page-aligned arrays.
- **`resize`.** `t.resize(shape)` discards the values and means exactly `t = tl::empty<T>(shape)`, so the capacity rule applies, and a shared tensor detaches from its copies. It matches `xt::xtensor::resize`.
- **Out of memory.** All allocations of an evaluation happen on the host while planning, so a failure surfaces at the trigger, not at the next wait. On failure, the core drains the deferred list, asks the resource to release its free blocks and retries once. If that fails too, it throws `tl::out_of_memory` with the space, the requested bytes, the bytes held by the pool and the live bytes, and leaves the window intact. The pool keeps its memory otherwise and only gives it back on `tl::release_memory(space)`. A cap on a space is set on the resource itself. Pools belong to the backend and are destroyed by `tl::finalize` before `Kokkos::finalize`; a tensor still alive at that point is reported.
- **NUMA.** No NUMA logic in v1. The documented configuration is one MPI rank per NUMA domain. A NUMA-aware resource (Umpire NUMA strategies, the `HostSpace` binding of kokkos#9193) can plug in later through the resource interface without touching the core.
- **Requirements from other tickets.** Packing buffers for `borrow_packed`, outputs of PETSc and Tpetra operator nodes, and the host side of Tpetra `DualView`s come from the resource of their space, like every other buffer.
- **Passed on:**
  - [Error reporting and debug mode](24-error-reporting-and-debug-mode.md): an out-of-memory error on one rank of a distributed run, NaN-filled storage after `resize` in debug mode, a tensor alive at `tl::finalize`;
  - [Zero-copy interop with PETSc and Tpetra](17-petsc-tpetra-interop.md): an assignment that changes the size of a wrapped tensor would leave the PETSc or Tpetra storage, so it is an error;
  - [Rerun the fusion benchmark on an HPC node and a GPU](19-rerun-fusion-benchmark-hpc-gpu.md): `ResourceAwarePool` against `QuickPool` on small allocations, and staggered offsets on a GPU.

## Comments

Grilling log (2026-10-30):

- Q1 in-place reuse: option B. Only the target of an assignment reuses its old buffer. The uniqueness test runs on the host at evaluation time, with window nodes counted as references. A buffer keeps a capacity; the target is reused when the new size fits and fills at least half of it. Donation of dying operands (JAX style) is deferred until a reference benchmark asks for it.
- Q2 Umpire: option B. Umpire is required by the Kokkos backend; the serial backend keeps aligned operator new. No home-grown fallback pool.
- Q3 allocator customisation: option B. A type-erased tl::memory_resource per memory space, queue-ordered like cuda::mr (allocate(bytes, alignment, queue), deallocate(ptr, bytes, alignment, queue)); default Umpire pool; tl::umpire_resource in the Kokkos backend, CCCL and RMM adapters in optional headers; set before the first allocation in that space, changing it later is an error.
- Q4 deferred frees: option A. On release the core joins all pending events onto the queue of the last access and calls deallocate(ptr, ..., queue); default pool is Umpire ResourceAwarePool from v1. A resource that is not queue-ordered declares it, and the core keeps a (ptr, event) list polled at each allocation and evaluation, drained by waiting on out-of-memory. Measure ResourceAwarePool against QuickPool on samurai's small allocations later.
- Q5 temporaries: option C. v1 allocates each temporary from the pool at its first writer and deallocates it in queue order right after its last reader is enqueued; the logical peak feeds the planned-bytes trigger. A per-window arena (XLA-style offset assignment) may replace it later behind the same planner interface if the evaluation cost budget asks for it. Library-operation workspaces use the same resource when the library allows it.
- Q6 staggered offsets: option A. A tl::staggered(resource) adaptor, on by default for host spaces and off for device spaces: above 64 KiB it over-allocates 4 KiB and shifts the start by (i x 64 B) mod 4 KiB with a per-space rotating counter, keeping 64 B alignment; cache line, page size and alignment come from backend capabilities. Acceptance test: ponio heat_bench rkc_202 at 10^6 cells. Device default revisited after the GPU benchmark ticket.
- Q7 resize: option B. t.resize(shape) discards values and is defined as *this = tl::empty<T>(shape), so the Q1 capacity rule applies; a shared tensor detaches. Debug mode may fill resized storage with NaN.
- Q8 out of memory: option A. Allocation happens on the host while planning, so failure surfaces at the trigger. On failure: drain the deferred list, release the resource's free blocks, retry once, then throw tl::out_of_memory (space, requested, pool-held and live bytes) with the window intact. The pool returns memory only through tl::release_memory(space); caps are set on the resource itself. Pools are destroyed by tl::finalize before Kokkos::finalize; a live tensor at that point is reported. Cross-rank OOM handling goes to ticket 24.
- Q9 NUMA: option C. No NUMA logic in v1; one MPI rank per NUMA domain is the documented configuration; a NUMA-aware resource (Umpire NUMA, kokkos#9193) can plug in later through the resource interface without touching the core.

## Amendment (2026-10-30)

[Error reporting and debug mode](24-error-reporting-and-debug-mode.md) and [ADR 0007](../../../docs/adr/0007-errors-poison-results-across-ranks.md): after the drain and the single retry, an out-of-memory failure during evaluation no longer throws at the trigger. It poisons the outputs of the window, and `tl::out_of_memory` (with the same fields) is thrown when one of them is read, on every rank of a distributed run.
