# Memory pools for HPC tensors

Ticket: [20-memory-pools-research](../issues/20-memory-pools-research.md)
Date of survey: 2026-10-30

## Question

Which existing allocators and memory pools can tensorlib use for tensor buffers and kernel temporaries on CPU and GPU, instead of writing its own? Covered here: Umpire (LLNL), RAPIDS RMM, the `cudaMallocAsync` and `hipMallocAsync` stream-ordered pools, SYCL USM, Kokkos memory spaces and Kokkos `MemoryPool`, and how PETSc and Trilinos (Tpetra) allocate. For each one: platforms, stream-ordered semantics, thread safety, fragmentation, how it plugs into Kokkos, licence and maintenance.

The prototype in [ticket 09](../issues/09-multi-output-fusion-prototype.md) showed why this matters. Allocating fresh output buffers on every evaluation took a large fused kernel from 8.49 ms to 14.7 ms on CPU, because the first touch faults in new pages.

## Method and confidence

- All facts come from source code, in-repo docs and issue threads on GitHub, read on 2026-10-30 with `gh api` and `raw.githubusercontent.com`. These are marked **[verified]**.
- The vendor doc sites (docs.nvidia.com, developer.nvidia.com, rocm.docs.amd.com, registry.khronos.org, petsc.org, umpire.readthedocs.io) all returned HTTP 403 to the fetcher. I used the GitHub copies instead: the HIP docs in `ROCm/rocm-systems`, the SYCL spec sources in `KhronosGroup/SYCL-Docs`, the CCCL docs folder, `NVIDIA/cuda-samples`, and the docs folders of Umpire and RMM.
- Conclusions I draw without a direct source are marked **[inference]**.

## Headline findings

1. **Kokkos-managed allocation is the wrong tool for tensor storage in a lazy, asynchronous library.** Each `Kokkos::View` free fences. `HostSpace::deallocate` calls a global `Kokkos::fence` before freeing. `CudaSpace` and `HIPSpace` call `cudaFree`/`hipFree`, or, with the opt-in `MallocAsync` options, wrap `cudaFreeAsync`/`hipFreeAsync` in a device synchronize on both sides. `SYCLSpace` fences before `sycl::free`. Kokkos also has no host-side memory pool. **[verified]** ([HostSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/impl/Kokkos_HostSpace.cpp), [CudaSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/Cuda/Kokkos_CudaSpace.cpp), [HIPSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/HIP/Kokkos_HIP_Space.cpp), [SYCLSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/SYCL/Kokkos_SYCL_Space.cpp))
2. **Umpire is the only surveyed pool that covers every tensorlib target**: host, CUDA, HIP and SYCL, with CI on Linux, macOS and Windows, under the MIT licence, with releases in 2026. It has a general-purpose coalescing pool (`QuickPool`) and a stream-aware pool (`ResourceAwarePool`) that defers reuse across streams until an event completes. **[verified]** ([Umpire](https://github.com/LLNL/Umpire))
3. **The Kokkos and Umpire teams are already building the bridge.** `llnl/umpire-kokkos` ships `UmpireSpace`, a Kokkos memory space backed by an Umpire allocator. It was presented at the Kokkos User Group 2026, and Kokkos core is removing internal macros to allow user-defined memory spaces like it. The Kokkos issue on memory space instances, which names pool-backed spaces as a primary use case, is still open. **[verified]** ([umpire-kokkos](https://github.com/llnl/umpire-kokkos), [kokkos#9588](https://github.com/kokkos/kokkos/pull/9588), [kokkos#9195](https://github.com/kokkos/kokkos/issues/9195))
4. **RMM is excellent but CUDA only.** It is stream-ordered and thread safe, but it builds only for CUDA, with recent toolchains (gcc 13.3+, nvcc 12.9+, CMake 4.0+). The ROCm port `hipMM` is archived. RMM can be an optional adapter for RAPIDS users, not the core pool. **[verified]** ([RMM](https://github.com/rapidsai/rmm), [hipMM](https://github.com/ROCm/hipMM))
5. **Native stream-ordered pools are useful building blocks with traps.** `cudaMallocAsync` and `hipMallocAsync` give true stream-ordered free, but by default the pool hands memory back at the next synchronization unless the release threshold is raised. Kokkos turned `cudaMallocAsync` off by default because of downstream problems, including IPC with MPI, and turned `hipMallocAsync` off for ROCm. SYCL 2020 has no stream-ordered allocator, and Intel's async-alloc extension is still only "proposed". **[verified]**
6. **PETSc and Tpetra each solved this locally rather than sharing a library.** PETSc has its own segmented, event-tracked device pool on top of `cudaMallocAsync`/`hipMallocAsync`. Tpetra keeps grow-only static scratch buffers and reuses `DualView`s instead of pooling. Neither exports its pool for others to use. **[verified]**

## Details per allocator

### Umpire (LLNL)

- **What it is.** "A resource management library that allows the discovery, provision, and management of memory on machines with multiple memory devices like NUMA and GPUs." MIT licence. Latest release v2026.07.2 (2026-10-08); earlier releases in 2026-08, 2025-12 and 2025-09. CI runs on GitHub Actions (ubuntu, macos-latest, windows-latest) and on LLNL machines (lassen, tioga, tuolumne, dane, corona). **[verified]** ([README](https://github.com/LLNL/Umpire/blob/develop/README.md), [build.yml](https://github.com/LLNL/Umpire/blob/develop/.github/workflows/build.yml), [.gitlab/jobs](https://github.com/LLNL/Umpire/tree/develop/.gitlab/jobs))
- **Resources.** Host, CUDA device/pinned/unified/constant, HIP device/pinned/unified/constant, SYCL device, file-backed, host shared memory and MPI-3 shared memory. The build options include CUDA, HIP, SYCL, OpenMP, MPI and NUMA. **[verified]** ([src/umpire/resource](https://github.com/LLNL/Umpire/tree/develop/src/umpire/resource), [CMakeLists.txt](https://github.com/LLNL/Umpire/blob/develop/CMakeLists.txt), [advanced_configuration.rst](https://github.com/LLNL/Umpire/blob/develop/docs/sphinx/advanced_configuration.rst))
- **QuickPool.** "A simple pooling algorithm that can fulfill requests for allocations of any size". It takes an initial block size and a minimum growth size, and the docs call it what "most Umpire users will make allocations that use the GPU via". **[verified]** ([quick_pool.rst](https://github.com/LLNL/Umpire/blob/develop/docs/sphinx/tutorial/quick_pool.rst))
- **Fragmentation.** The docs name the bad pattern ("several allocations of incrementing size where each allocation is larger than the previous block size"). The fix is coalescing: free blocks go back to the resource and a single block of the tallied size, or of the high watermark, replaces them. Coalescing runs automatically through `percent_releasable` or `blocks_releasable` heuristics, or on demand. **[verified]** ([quick_pool_heuristics.rst](https://github.com/LLNL/Umpire/blob/develop/docs/sphinx/cookbook/quick_pool_heuristics.rst), [coalesce_pool.rst](https://github.com/LLNL/Umpire/blob/develop/docs/sphinx/cookbook/coalesce_pool.rst))
- **Stream semantics.** `QuickPool` frees on the host at once. The Umpire docs say this is safe with one device stream, because kernels on a stream run in order. With several streams, `ResourceAwarePool` adds a "pending" state: memory freed on stream r1 can be reused only by r1 until the deallocation completes. It tracks streams as camp resources and checks events. **[verified]** ([resource_aware_pool.rst](https://github.com/LLNL/Umpire/blob/develop/docs/sphinx/cookbook/resource_aware_pool.rst), [ResourceAwarePool.cpp](https://github.com/LLNL/Umpire/blob/develop/src/umpire/strategy/ResourceAwarePool.cpp))
- **Plugging Kokkos streams in.** camp can wrap streams it did not create: `camp::resources::Cuda::CudaFromStream(cudaStream_t)`, `Hip::HipFromStream`, `Sycl::SyclFromQueue`. These match the `cuda_stream()`, `hip_stream()` and `sycl_queue()` accessors that [ticket 03](../issues/03-jit-with-kokkos.md) relies on. **[verified]** ([camp/resource](https://github.com/LLNL/camp/tree/main/include/camp/resource))
- **Thread safety.** `QuickPool` and `ResourceAwarePool` have no internal lock, and Umpire provides `ThreadSafeAllocator` to wrap them. **[verified]** ([QuickPool.cpp](https://github.com/LLNL/Umpire/blob/develop/src/umpire/strategy/QuickPool.cpp), [thread_safe.rst](https://github.com/LLNL/Umpire/blob/develop/docs/sphinx/cookbook/thread_safe.rst))
- **Kokkos integration.** `llnl/umpire-kokkos` (MIT, created 2025-10, last push 2026-03) contains `UmpireSpace.hpp`, a memory space template over an existing Kokkos space that allocates from a named Umpire allocator. Its README says Kokkos "does not currently support memory pools" and that the header will move into the Umpire repo. Today the header depends on `Kokkos::Impl::SharedAllocationRecord` and specializes `Kokkos::Impl::DeepCopy`, which ties it to Kokkos internals. **[verified]** ([umpire-kokkos](https://github.com/llnl/umpire-kokkos), [UmpireSpace.hpp](https://github.com/llnl/umpire-kokkos/blob/main/UmpireSpace.hpp)). A Kokkos maintainer wrote in [kokkos#9588](https://github.com/kokkos/kokkos/pull/9588) (merged 2026-09-25) that the work aims at "user-defined memory spaces, to enable things like `UmpireSpace`", with customizable access traits and deep copy as the next step. **[verified]**
- **Adoption.** PETSc's configure system can download and build Umpire (v2025.12.0) as an external package. **[verified]** ([Umpire.py](https://github.com/petsc/petsc/blob/main/config/BuildSystem/config/packages/Umpire.py))

### RAPIDS RMM

- Memory resources follow the CCCL `cuda::mr` resource concept with `allocate(cuda::stream_ref, bytes, alignment)` and `deallocate(stream, ptr, bytes, alignment)`. Memory may be reused on the same stream without synchronization. Using it on another stream without an event or sync is undefined behaviour. **[verified]** ([README](https://github.com/rapidsai/rmm/blob/main/README.md))
- Resources: `cuda_memory_resource`, `managed_memory_resource`, `pool_memory_resource` (coalescing best fit), `arena_memory_resource` (global, per-thread and per-stream arenas, address-ordered first fit, "emphasizes fragmentation avoidance and scalable concurrency"), `fixed_size`, `binning`, `cuda_async_memory_resource`, and adaptors for logging, statistics, limits and thread safety. All device resources are thread safe for `allocate` and `deallocate`. **[verified]** ([include/rmm/mr](https://github.com/rapidsai/rmm/tree/main/cpp/include/rmm/mr), [arena_memory_resource.hpp](https://github.com/rapidsai/rmm/blob/main/cpp/include/rmm/mr/arena_memory_resource.hpp))
- `cuda_async_memory_resource` sets the release threshold to `UINT64_MAX` by default "so that the pool retains memory across synchronization events". **[verified]** ([cuda_async_memory_resource.hpp](https://github.com/rapidsai/rmm/blob/main/cpp/include/rmm/mr/cuda_async_memory_resource.hpp))
- Requirements: gcc 13.3+, nvcc 12.9+, CMake 4.0+, CUDA 12.2+, compute capability 7.0+. Apache-2.0. Release v26.10.00 (2026-10-07). **[verified]**. The AMD port `ROCm/hipMM` is archived (last push 2025-05). **[verified]**. RMM supports neither CPU-only builds, HIP nor SYCL, and it is not tested with MSVC or Apple Clang. **[inference]** from the stated toolchain.

### CUDA and HIP stream-ordered allocators

- `cudaMallocAsync`/`cudaFreeAsync` allocate from a `cudaMemPool_t` in stream order. The CUDA sample says that after a synchronization the pool releases memory to the OS unless the application raises the release threshold, which the sample sets to `ULONG_MAX`. The sample lists Linux and Windows. **[verified]** ([streamOrderedAllocation.cu](https://github.com/NVIDIA/cuda-samples/blob/master/cpp/2_Concepts_and_Techniques/streamOrderedAllocation/streamOrderedAllocation.cu))
- CCCL 3.2 / CUDA 13.2 wraps these pools as `cuda::device_memory_pool`, with `release_threshold`, reuse policies and usage statistics, behind the same `cuda::mr` concept RMM uses. Host pools need CUDA 12.9+. Managed pools need CUDA 13.0+ and are not supported on Windows. **[verified]** ([memory_pools.rst](https://github.com/NVIDIA/cccl/blob/main/docs/libcudacxx/runtime/memory_pools.rst))
- HIP has the same API (`hipMallocAsync`, `hipMemPoolCreate`, `hipMallocFromPoolAsync`, `hipMemPoolAttrReleaseThreshold`, `hipMemPoolTrimTo`, reuse-policy flags). The HIP docs say that when the pool holds more than the threshold, "the allocator tries to release memory back to the operating system during the next call to stream, event, or context synchronization". **[verified]** ([stream_ordered_allocator.rst](https://github.com/ROCm/rocm-systems/blob/develop/projects/hip/docs/how-to/hip_runtime_api/memory_management/stream_ordered_allocator.rst))
- **Kokkos's use of them.** Kokkos 4.2 made `cudaMallocAsync` the default, and 4.4 reverted it "given all the problems that users reported" ([#7353](https://github.com/kokkos/kokkos/pull/7353)). The CMake comment cites issues with IPC and older UCX as the MPI layer. A maintainer closed a pool-size patch with: "we anyway moved away again from cudaMallocAsync due to too much problems downstream since it doesn't allow IPC. We will revisit memory pools as an explicit feature" ([#7032](https://github.com/kokkos/kokkos/pull/7032)). `hipMallocAsync` is now off by default, and CMake warns that it "is problematic with ROCm 7" ([#9022](https://github.com/kokkos/kokkos/pull/9022), [kokkos_enable_options.cmake](https://github.com/kokkos/kokkos/blob/develop/cmake/kokkos_enable_options.cmake)). Even when enabled, Kokkos synchronizes the device after the async malloc and before and after the async free, uses the async path only for allocations of 40 kB or more on CUDA, and never sets a release threshold, so the stream ordering buys nothing. **[verified]** ([CudaSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/Cuda/Kokkos_CudaSpace.cpp), [HIPSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/HIP/Kokkos_HIP_Space.cpp))

### SYCL USM

- SYCL 2020 `sycl::free` requires that "there are no in-progress or enqueued commands using the memory", and "whether free is blocking or non-blocking is unspecified". So it is not stream ordered, and the standard has no pool. **[verified]** ([programming_interface.adoc](https://github.com/KhronosGroup/SYCL-Docs/blob/main/adoc/chapters/programming_interface.adoc))
- Intel's `sycl_ext_oneapi_async_memory_alloc` adds `async_malloc_from_pool` and `async_free` on a queue, with a memory pool and a reserve threshold. Its status is "proposed": "Shipping software products should not rely on APIs defined in this specification." **[verified]** ([extension spec](https://github.com/intel/llvm/blob/sycl/sycl/doc/extensions/proposed/sycl_ext_oneapi_async_memory_alloc.asciidoc))
- Kokkos fences before `sycl::free`. **[verified]** ([SYCLSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/SYCL/Kokkos_SYCL_Space.cpp))

### Kokkos memory spaces and `MemoryPool`

- Allocation through a View goes to the memory space's `allocate`/`deallocate`. `HostSpace` uses aligned `operator new` and runs a global `Kokkos::fence` before every non-null free. **[verified]** ([HostSpace](https://github.com/kokkos/kokkos/blob/develop/core/src/impl/Kokkos_HostSpace.cpp)). Plain `cudaFree` also synchronizes the device. **[inference]** (documented CUDA behaviour; NVIDIA docs blocked here).
- `MemoryPool<DeviceType>` lives in namespace `Kokkos` (not `Kokkos::Experimental`) in `core/src/Kokkos_MemoryPool.hpp`. It is a fixed-capacity pool built from superblocks with concurrent bitsets. `allocate` is a `KOKKOS_FUNCTION`, callable from kernels, and may fail under concurrency (`attempt_limit`). Blocks are powers of two, with a default minimum of 64 B, a default maximum of 4 KB and a hard cap of 2 GB per superblock, and requests above the maximum block size abort. **[verified]** ([Kokkos_MemoryPool.hpp](https://github.com/kokkos/kokkos/blob/develop/core/src/Kokkos_MemoryPool.hpp)). It was built for in-kernel allocation (tasking, hash tables), not for multi-gigabyte tensor buffers allocated from the host. **[inference]**
- There is no supported way today to make a View allocate from a pool. Issue [#5794](https://github.com/kokkos/kokkos/issues/5794) "Allocate View from MemoryPool?" is open, and maintainers pointed to a KUG talk on Umpire. Issue [#2114](https://github.com/kokkos/kokkos/issues/2114) (host-side allocator for CUDA memory, opened 2019) was closed in 2026-10 "as superseded by broader memory-space instance design", tracked in [#9195](https://github.com/kokkos/kokkos/issues/9195). That issue lists "memory spaces that are backed by memory pools" as the first use case and says "we need a way to deal with async (stream aware) allocations". **[verified]**
- What works today is an unmanaged View over a pointer tensorlib allocated itself. This is the path [ticket 03](../issues/03-jit-with-kokkos.md) already uses for JIT kernels. **[verified]** (ticket 03)

### PETSc

- `PetscDeviceAllocate_Private` is documented as "Asynchronous, Auto-dependency aware" and goes through the device context's `memalloc`. Without device support it falls back to `PetscMalloc`. **[verified]** ([memory.cxx](https://github.com/petsc/petsc/blob/main/src/sys/objects/device/interface/memory.cxx))
- The CUDA/HIP device context uses PETSc's own `SegmentedMemoryPool`. Each chunk records an event and the id of the stream that released it. The same stream may claim it again at once, and another stream must wait for the event or skip the chunk. Its device allocator underneath calls `cupmMallocAsync`/`cupmFreeAsync` on the context's stream. **[verified]** ([segmentedmempool.hpp](https://github.com/petsc/petsc/blob/main/src/sys/objects/device/impls/segmentedmempool.hpp), [cupmallocator.hpp](https://github.com/petsc/petsc/blob/main/src/sys/objects/device/impls/cupm/cupmallocator.hpp))
- PETSc's Kokkos vectors allocate through Kokkos `DualView` constructors or wrap PETSc arrays as unmanaged Views, so they use Kokkos allocation, not the pool. **[verified]** ([veckok.kokkos.cxx](https://github.com/petsc/petsc/blob/main/src/vec/vec/impls/seq/kokkos/veckok.kokkos.cxx))

### Trilinos (Tpetra)

- Tpetra has no general pool. `Tpetra::Details::StaticKokkosAllocation<Space>::resize` keeps one grow-only scratch buffer per memory space, freed at `Kokkos::finalize`. `reallocDualViewIfNeeded` takes a subview of a buffer that is already big enough, and reallocates (with a fence) only when the buffer is too small or more than `tooBigFactor` too large, because "reallocation ... is expensive for some memory spaces". **[verified]** ([Tpetra_Details_StaticView.hpp](https://github.com/trilinos/Trilinos/blob/develop/packages/tpetra/core/src/Tpetra_Details_StaticView.hpp), [Tpetra_Details_reallocDualViewIfNeeded.hpp](https://github.com/trilinos/Trilinos/blob/develop/packages/tpetra/core/src/Tpetra_Details_reallocDualViewIfNeeded.hpp))

## What this means for tensorlib

- Under [ADR 0001](../../../docs/adr/0001-value-semantics-with-copy-on-write.md) a buffer is released when its last handle dies. Under [ADR 0002](../../../docs/adr/0002-implicit-pending-windows.md) a kernel that reads it may still be running. A free that fences, which is what every Kokkos memory space does, would serialize asynchronous evaluation. tensorlib therefore needs frees that are deferred or stream ordered. **[inference]**
- On CPU, a pool that keeps pages mapped removes the first-touch cost the prototype measured once it is warm. Pages keep the NUMA placement of their first toucher, so the first kernel should touch buffers with the same thread layout as later kernels. Umpire's NUMA support and the HostSpace NUMA binding proposed in [kokkos#9193](https://github.com/kokkos/kokkos/pull/9193) are options for later. **[inference]**
- Pooled memory is freed back to the driver less often. That should also keep the registration caches of CUDA-aware MPI valid. The IPC problems Kokkos reported concern `cudaMallocAsync` pools, not `cudaMalloc`-backed sub-allocators such as Umpire `QuickPool` over `DEVICE`. This needs checking on a real node. **[inference]**

## Recommendation

1. **Depend on Umpire** as the pool behind the backend's allocator interface. Use `QuickPool` per memory space (host, device, pinned) for buffers used on one Kokkos execution space instance. Switch to `ResourceAwarePool` once evaluation uses several Kokkos instances, wrapping Kokkos's own streams with `CudaFromStream`/`HipFromStream`/`SyclFromQueue`. Wrap either pool in `ThreadSafeAllocator`, since there is one pending window per host thread. Keep Umpire optional at build time so that the serial backend and minimal builds still work, with plain aligned `operator new` as the fallback.
2. **Allocate raw memory and wrap it as unmanaged Kokkos Views.** Do not let Kokkos allocate tensor storage. Kokkos still owns execution spaces and streams, as [ticket 03](../issues/03-jit-with-kokkos.md) decided, but storage lifetime belongs to tensorlib's refcounted storage. Track `UmpireSpace` and Kokkos memory space instances ([#9195](https://github.com/kokkos/kokkos/issues/9195)), and move to them once Kokkos supports user-defined memory spaces without `Impl` specializations.
3. **Offer native stream-ordered pools and RMM as optional adapters, not the default.** That means CCCL `cuda::device_memory_pool` and `hipMallocFromPoolAsync` with the release threshold raised, and RMM for applications that already run a RAPIDS memory resource. Do not rely on Kokkos's `IMPL_*_MALLOC_ASYNC` options.
4. **Do not use** Kokkos `MemoryPool` for tensor buffers. It has a fixed capacity and blocks of 4 KB by default. It could serve in-kernel scratch later. Do not copy PETSc's or Tpetra's internal schemes either, because they are not reusable libraries.

## Remaining gap

- **Deferred free tied to evaluation events.** Umpire's `ResourceAwarePool` covers device streams through camp events. tensorlib still has to record, on each evaluation, which buffers its kernels read, so that a CoW release during a pending launch returns memory only after the matching event or fence. This is a small layer over Umpire, not a new allocator.
- **Planning temporaries inside a window.** The graph knows every buffer lifetime before it launches, so it can assign temporaries to a few reused slots, as XLA's buffer assignment does. No allocator does this. It belongs to [Buffer reuse and allocation](../issues/21-buffer-reuse-and-allocation.md).
- **Deterministic limits.** ADR 0002 requires resource-limit triggers to be deterministic across ranks. Pool statistics (current size, high watermark) can differ between ranks, so limits must count logical bytes requested, not pool state. **[inference]**
- **SYCL.** There is no portable stream-ordered free until the oneAPI extension ships. Umpire over SYCL USM plus host-side deferral is the only option.
