# Requirements from samurai and ponio

Ticket: [25-samurai-ponio-requirements](../issues/25-samurai-ponio-requirements.md)
Date of survey: 2026-10-30

## Question

How do samurai (AMR and multiresolution on interval-based meshes) and ponio (time integration) use array libraries today, and what does that require from tensorlib's core? The full list of sub-questions is in the ticket.

## Method and confidence

- Both repositories were cloned with `git clone --depth 1` on 2026-10-30 and read, not built. samurai at [`9e77d1a`](https://github.com/hpc-maths/samurai/tree/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d) (2026-10-29), ponio at [`c75d011`](https://github.com/hpc-maths/ponio/tree/c75d011348c78642e27f5975f5cfa76f624820b0) (2026-10-27). Line links below point at these commits.
- Issues and pull requests were read with `gh api` (search for xtensor, performance, compile time, GPU, Kokkos, OpenMP, benchmark, expression).
- Facts read in the code or in a PR are marked **[verified]**. Timings come from the PR descriptions written by the authors and are marked **[PR]**. Conclusions without a direct source are marked **[inference]**.

Short link prefixes used below: `S/` is `https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/`, `P/` is `https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/`.

## Headline findings

1. **samurai's hot loops have already left xtensor.** Over 2026, samurai rewrote prediction, projection, detail computation, the linear flux schemes and the LBM stream as raw-pointer loops over precomputed offsets, with timings like 7.7 s to 1.5 s and 11.8 s to 0.36 s. xtensor stays for field storage, for whole-field expressions and for small fixed arrays. **[verified, PR]**
2. **A samurai field is a flat 1D array (or `N x n_comp`, AoS) over all cells of all levels of one rank, ghosts included.** The mesh, not the array, gives the meaning of each position: an interval `[a, b)` at level `l` and row `(j, k)` maps cell `i` to storage index `index + i`. There is no global index space and no regular shape. **[verified]**
3. **The natural iteration space is a list of intervals, not an n-d box.** Each operator runs a short affine loop per interval, with different offsets and strides (1 or 2) per operand and per level. Many intervals are tens of cells long. **[verified for the structure; interval lengths are an inference]**
4. **The mesh, and so every field shape, changes at every time step** (mesh adaptation rebuilds the mesh and transfers the fields). ponio's stage buffers are resized through a callback at each step. **[verified]**
5. **Most of the physics is in user lambdas on small fixed-size arrays** (non-linear fluxes, cell-based schemes, Jacobians, boundary conditions, LBM collisions). ADR 0003 keeps user lambdas out of the IR. **[verified]**
6. **ponio needs exactly what the multi-output fusion work targets:** `ui = un + dt * (a_i1*k1 + ... + a_i,i-1*k_i-1)` with up to 20 operands (`rkc_202`), run-time scalars, `std::swap` of states and in-place `f(t, y, dy)`. Today it gets one loop either from the state type's own expression templates or from ponio's minimal expression layer. **[verified]**
7. **Neither library runs on GPUs today.** samurai's philosophy page lists GPU acceleration among the AMReX features samurai does not provide. Parallelism is OpenMP tasks per interval plus `omp simd`, and MPI through Boost.MPI with samurai's own domain decomposition and load balancing. **[verified]**

## samurai

### Array libraries and the storage layer

- Dependencies: xtensor (>= 0.26) by default, Eigen 3 as an alternative, chosen at configure time by three CMake cache variables: `SAMURAI_FIELD_CONTAINER` (xtensor, eigen3), `SAMURAI_FLUX_CONTAINER` (array, xtensor, eigen3) and `SAMURAI_STATIC_MAT_CONTAINER` (xtensor, eigen3) ([S/CMakeLists.txt#L63-L73](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/CMakeLists.txt#L63-L73), [#L170-L196](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/CMakeLists.txt#L170-L196)). Other dependencies: HighFive, pugixml, fmt, CLI11; optional OpenMP, Boost.MPI and Boost.Serialization, PETSc, ParMETIS, PT-Scotch ([#L202-L238](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/CMakeLists.txt#L202-L238)). C++20. **[verified]**
- The pluggable layer is `include/samurai/storage/`. [`containers_config.hpp#L33-L64`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/storage/containers_config.hpp#L33-L64) picks `field_data_storage_t`, `local_field_data_t`, `default_view_t` and the static `Array` from either backend. The xtensor backend stores a field as `xt::xtensor<T, 1>` for a scalar field and `xt::xtensor<T, 2>` of shape `{N, n_comp}`, row major, for a vector field ([`xtensor.hpp#L21-L67`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/storage/xtensor/xtensor.hpp#L21-L67)), and exposes `view(container, range)` helpers that return `xt::view(..., xt::range(start, end, step))` ([#L92-L152](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/storage/xtensor/xtensor.hpp#L92-L152)). Small arrays are `xt::xtensor_fixed` ([`xtensor_static.hpp`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/storage/xtensor/xtensor_static.hpp)). **[verified]**
- The layer leaks. 65 headers use `xt::` directly (93 calls to `xt::view`, `xt::eval`, `xt::noalias`, `xt::xtensor<` or `xt::adapt` alone), field access overloads take `xt::xtensor_fixed` indices ([`access_base.hpp#L85-L103`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/field/access_base.hpp#L85-L103)), and the mesh API uses `xt::xtensor_fixed` for coordinates ([`level_cell_array.hpp#L82-L83`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/level_cell_array.hpp#L82-L83)). The Eigen options do not compile today ([issue #628](https://github.com/hpc-maths/samurai/issues/628)). PR [#222](https://github.com/hpc-maths/samurai/pull/222), which added the Eigen container, already reported bugs from mixing row and column major in views and lazy evaluation. **[verified]**
- Vector fields are AoS only. PR [#463](https://github.com/hpc-maths/samurai/pull/463) (2026-07) removed the SoA variant and its `bool SOA` template parameter everywhere; [`vector_field.hpp#L38`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/field/vector_field.hpp#L38) uses `field_data_storage_t<value_t, n_comp, false>`. A size-1 component dimension "collapses" to a scalar (`CollapsableArray`). **[verified]**
- Index types: coordinates are `int`, storage offsets `signed long long` ([`samurai_config.hpp#L57-L59`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/samurai_config.hpp#L57-L59)). **[verified]**

### Mesh, intervals and field access

- An `Interval` is `{start, end, step, index}`; the value of cell `c` sits at `index + c` in the storage ([`interval.hpp#L23-L64`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/interval.hpp#L23-L64)). Multiplying an interval scales `start`, `end` and `step` ([#L174-L180](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/interval.hpp#L174-L180)), so `field(level + 1, 2 * i)` is a stride-2 view. **[verified]**
- The philosophy page states the design: store intervals, not cells; field values are contiguous along x so "a scheme applied to an interval works on whole arrays"; looking up an isolated cell is slow (a search per direction); "a level is immutable", so adaptation builds a new mesh and transfers the fields ([`docs/source/philosophy.md#L29-L68`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/docs/source/philosophy.md#L29-L68)). Mesh operations are a lazy set algebra (`intersection`, `union_`, `difference`, `translate`, `expand`, `contract`, `.on(level)`), and a "subset operator" kernel then runs on every interval of the result ([#L84-L116](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/docs/source/philosophy.md#L84-L116)). **[verified]**
- `field(level, i, j)` calls `get_interval`, which searches the mesh (`find`) for the interval holding `(i.start, j)` and builds a view `{index + start, index + end, step}` on the flat storage ([`access_base.hpp#L69-L74`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/field/access_base.hpp#L69-L74), [`level_cell_array.hpp#L656-L668`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/level_cell_array.hpp#L656-L668)). Every leaf of every per-interval expression pays one search. **[verified]**
- The storage covers the `reference` mesh, which holds cells plus ghosts of every kind (MPI subdomain, periodic, prediction and projection ghosts, all levels) in one numbering (`MRMeshId` in [`mr/mesh.hpp#L25-L33`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/mr/mesh.hpp#L25-L33)). Ghosts are interleaved with owned cells, not a band around them. **[verified]**
- On the p4est `simple2` example, the mesh structure costs 0.51 bytes per cell at level 9 (66,379 cells, 33,688 bytes) ([philosophy.md#L69-L77](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/docs/source/philosophy.md#L69-L77)). With 24-byte intervals that is at most about 1,400 intervals, so around 50 cells per interval on average in that case. **[inference]**

### Access patterns in hot loops

- **Whole-field expressions.** `unp1 = u - dt * conv(u)` ([`advection_2d.cpp#L140`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/demos/FiniteVolume/advection_2d.cpp#L140)) and the SSP-RK3 stages of [`burgers.cpp#L267-L269`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/demos/FiniteVolume/burgers.cpp#L267-L269). samurai plugs its own `field_expression` tag into xtensor's operator dispatch ([`field_expression.hpp#L131-L149`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/field_expression.hpp#L131-L149)), then assigns by looping over every interval of the mesh and doing `noalias(dest(level, i, index)) = e(level, i, index)` ([`field_base.hpp#L231-L242`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/field/field_base.hpp#L231-L242)). Each node calls `eval(...)` "needed by eigen", which materialises a temporary per node and per interval ([`field_expression.hpp#L106-L111`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/field_expression.hpp#L106-L111)). Since all operands live on the same mesh, the same result is a single flat loop over the storage. **[verified; the flat-loop equivalence is an inference that holds whenever all operands share one mesh]**
- **Operators return new fields.** `conv(u)` allocates an output field and fills it with zeros at each call ([`explicit_FV_scheme.hpp#L57-L73`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/explicit_FV_scheme.hpp#L57-L73)). **[verified]**
- **Prediction and projection** (inter-level operators of multiresolution) compute the storage offset of the first cell of each stencil row once per interval, then loop with raw pointers, `data[(offset + i) * n_comp + n]`, fine index `2 * i` ([`projection.hpp#L22-L64`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/numeric/projection.hpp#L22-L64), [`prediction.hpp#L156-L264`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/numeric/prediction.hpp#L156-L264)). The stencil shape and the prediction coefficients are compile-time (`static_nested_loop`, `ce_pow(order, dim)`), N-dimensional since PR [#435](https://github.com/hpc-maths/samurai/pull/435) (tested up to 6D). Tuple versions apply several (dest, src) pairs in one traversal of the interval set (PR [#451](https://github.com/hpc-maths/samurai/pull/451)), which is multi-output fusion done by hand. **[verified]**
- **Detail computation** uses xtensor-style views with stride 2: `detail(level + 1, 2 * i) = field(level + 1, 2 * i) - field(level, i)` ([`mr/operators.hpp#L152-L153`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/mr/operators.hpp#L152-L153)); 2D and 3D were moved to raw loops by PR [#481](https://github.com/hpc-maths/samurai/pull/481). **[verified]**
- **Linear flux schemes** (`LinearHomogeneous`) loop per interface interval with `#pragma omp simd` on `field_value(out, idx + ii, c) += coeff * field_value(in, idx_s + ii, c)` for each stencil point, with a pairwise fine-to-coarse sum at level jumps ([`explicit_flux_based_scheme__lin_hom.hpp#L57-L163`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/flux_based/explicit_flux_based_scheme__lin_hom.hpp#L57-L163)). In the OpenMP path, contributions go into local buffers and then into the output with `omp atomic update`, because two interfaces can write the same cell ([#L250-L262](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/flux_based/explicit_flux_based_scheme__lin_hom.hpp#L250-L262)). **[verified]**
- **Non-linear flux schemes** copy the stencil values of each interface into a small array (`StencilValues`, `xtensor_fixed` based), call the user's flux lambda, and scatter the result with atomics ([`flux_based_scheme__nonlin.hpp#L151-L156`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/flux_based/flux_based_scheme__nonlin.hpp#L151-L156), [#L313-L325](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/flux_based/flux_based_scheme__nonlin.hpp#L313-L325), [`explicit_flux_based_scheme__nonlin.hpp#L52-L61`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/flux_based/explicit_flux_based_scheme__nonlin.hpp#L52-L61)). Flux lambdas use `xtensor_fixed` arithmetic and `xt::col` on fixed Jacobian matrices ([`convection_nonlin.hpp#L291-L321`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/schemes/fv/operators/convection_nonlin.hpp#L291-L321)). Cell-based schemes take a per-cell lambda as well (example in ponio, [`bz_2d_pirock.cpp#L150-L180`](https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/ponio/examples/bz_2d_pirock.cpp#L150-L180)). **[verified]**
- **Masks** are applied by scalar loops (`apply_on_masked`, [`xtensor.hpp#L268-L302`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/storage/xtensor/xtensor.hpp#L268-L302)). Cell tags for adaptation are `uint8` bit flags handled with raw loops ([`mr/operators.hpp#L35-L85`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/mr/operators.hpp#L35-L85)). **[verified]**
- **Reductions**: per-component max of `|field|` for the relative detail, now a per-interval raw loop (PR [#481](https://github.com/hpc-maths/samurai/pull/481)); error norms in [`numeric/error.hpp`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/numeric/error.hpp). **[verified]**

### Parallelism and distribution

- OpenMP: one `omp task` per interval inside `omp parallel` / `omp single` ([`algorithm.hpp#L175-L194`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/algorithm.hpp#L175-L194), [#L242-L262](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/algorithm.hpp#L242-L262)), `omp simd` inside intervals (PR [#182](https://github.com/hpc-maths/samurai/pull/182)), atomics for scatters. **[verified]**
- MPI: Boost.MPI. Each rank owns a subdomain and a list of neighbours with copies of their meshes. A ghost exchange computes, per level and per neighbour, the intersection of the two meshes and the subdomain, packs `field(level, i, index)` interval by interval into a `std::vector`, and exchanges with `isend`/`irecv`; all fields go in one buffer per neighbour ([`update_ghost_mr.hpp#L56-L118`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/algorithm/update_ghost_mr.hpp#L56-L118), [#L145-L185](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/algorithm/update_ghost_mr.hpp#L145-L185)). The comments explain why levels cannot be merged: projection from level L to L-1 reads ghosts just synchronised at level L. **[verified]**
- Load balancing moves cells between ranks with SFC, diffusion, ParMETIS or PT-Scotch strategies ([`load_balancing/strategies/`](https://github.com/hpc-maths/samurai/tree/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/load_balancing/strategies), PR [#443](https://github.com/hpc-maths/samurai/pull/443)). In 2025 the authors said MPI with adaptation was not yet efficient, load balancing being the main challenge ([issue #322](https://github.com/hpc-maths/samurai/issues/322)). **[verified]**
- PETSc: field storage is wrapped without copy with `VecCreateSeqWithArray(..., f.data(), ...)` ([`petsc/utils.hpp#L50-L60`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/petsc/utils.hpp#L50-L60)). **[verified]**
- GPU: none. The philosophy page says AMReX offers "GPU acceleration with CUDA, HIP or SYCL backends"; samurai "provides none of these" ([philosophy.md#L233](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/docs/source/philosophy.md#L233)). No issue or PR mentions GPU or Kokkos. **[verified]**

### Mesh adaptation and field transfer

- The demos adapt the mesh at every time step, then `unp1.resize()` ([`advection_2d.cpp#L126-L142`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/demos/FiniteVolume/advection_2d.cpp#L126-L142)). `update_fields` builds new fields on the new mesh, copies unchanged cells interval by interval, projects coarsened cells and predicts refined ones, then swaps ([`update_fields.hpp#L28-L71`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/algorithm/update_fields.hpp#L28-L71), [#L120-L130](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/include/samurai/algorithm/update_fields.hpp#L120-L130)). So every field is reallocated with a new size at every step. **[verified]**

### Pain points recorded in PRs

- PR [#481](https://github.com/hpc-maths/samurai/pull/481): `detail.array() *= inv_max_fields_xt`, an xtensor broadcast of an `n_comp` vector over the detail array, "does not vectorize" and took about 5.1 s of the 7.2 s detail computation. Raw loops: detail computation 7.7 s to 1.5 s, time loop 36.8 s to 30.7 s on `euler_2d`, single thread. **[PR]**
- PR [#484](https://github.com/hpc-maths/samurai/pull/484): replacing lazy xtensor expressions with scalar loops over a reused buffer, together with hoisted stencils, cut the LBM stream from 11.8 s to 0.36 s (total 13.5 s to 2.0 s) on D2Q5444 Rayleigh-Taylor. **[PR]**
- PR [#474](https://github.com/hpc-maths/samurai/pull/474) and the set algebra benchmarks ([`benchmark/SET_ALGEBRA.md`](https://github.com/hpc-maths/samurai/blob/9e77d1afdb733a5d3af9257a9c02cdecd4c7013d/benchmark/SET_ALGEBRA.md)): rebuilding interval lists is a cost of its own, measured as time per emitted interval. **[verified]**
- PR [#485](https://github.com/hpc-maths/samurai/pull/485): the static set algebra encodes the expression tree in types; a run-time version for bindings is 10x to 40x slower and "not meant for the hot inlined loops". The same trade-off tensorlib made in ticket 11, made independently for sets. **[PR]**
- Compile time: PR [#414](https://github.com/hpc-maths/samurai/pull/414) ("Improve compile time", no description), PR [#455](https://github.com/hpc-maths/samurai/pull/455) (CI build time) and PR [#788](https://github.com/hpc-maths/samurai/pull/788), which builds the coverage job with two parallel jobs "to stay within the runner memory". No measured numbers. **[verified]**

### Stages and linear combinations

- Explicit RK stage `I`: `ui = un + dt * sum_j A[I][j] * Kj`, then `f(tn + c[I] * dt, ui, Ki)` ([`runge_kutta/erk.hpp#L40-L57`](https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/ponio/include/ponio/runge_kutta/erk.hpp#L40-L57)). The sum is a fold expression over `std::index_sequence<I>` ([`detail.hpp#L122-L133`](https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/ponio/include/ponio/detail.hpp#L122-L133)), so stage `I` of an `s`-stage method combines `I + 1` states in one expression, zero coefficients included. **[verified]**
- Butcher tableaux are `constexpr std::array<std::array<value_t, N>, N>` ([`butcher_tableau.hpp#L24-L25`](https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/ponio/include/ponio/butcher_tableau.hpp#L24-L25)), generated from 97 JSON files in [`database/`](https://github.com/hpc-maths/ponio/tree/c75d011348c78642e27f5975f5cfa76f624820b0/database) by a Jinja template. `rkc_202` has 20 stages and a dense lower-triangular `A` (190 non-zero entries), so its last stages combine 20 arrays. **[verified]**
- ROCK and RKC use three-term recurrences on a run-time number of stages: `uj = dt * mu * f_tmp - nu * ujm1 - kappa * ujm2`, then rotation by `std::swap` ([`runge_kutta/rock.hpp#L441-L477`](https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/ponio/include/ponio/runge_kutta/rock.hpp#L441-L477)). Coefficients come from tables at run time. **[verified]**
- Lawson methods apply a user-provided exponential to the linear part, `m_exp(c * dt * L) * ui`: for Eigen, a dense matrix-vector product ([`runge_kutta/lrk.hpp#L60-L69`](https://github.com/hpc-maths/ponio/blob/c75d011348c78642e27f5975f5cfa76f624820b0/ponio/include/ponio/runge_kutta/lrk.hpp#L60-L69)). **[verified]**
- The right-hand side writes into its output by reference, `f(t, y, dy)`, since PR [#84](https://github.com/hpc-maths/ponio/pull/84) ("Improve performance by adding output by reference", "remove useless allocation"). **[verified]**

## Requirements for tensorlib

Each requirement names the map ticket that owns it.

1. **Segmented iteration spaces in the IR.** One kernel must run over a list of intervals (segments), each with its own base offsets per operand, and an affine map inside each segment (stride 1 or 2, level shift). Without this, each samurai interval becomes one kernel launch over tens of cells, and launch and recording costs (about 0.5 us per evaluation and 5 ns per node, from ticket 09) exceed the work. The segment tables come from the host set algebra and change at every adaptation, so they are kernel arguments, not part of the kernel cache key. Owner: [Kernel IR](../issues/22-kernel-ir.md), with [Views and slicing](../issues/23-views-and-slicing.md) for the user-facing form.
2. **A user-facing view built from an index table.** samurai's `field(level, i, j)` would become a view selected by precomputed interval offsets (a gather of contiguous runs). It must be writable (`detail(level + 1, 2 * i) = ...`), and when it is the target of an assignment it must keep in-place semantics without breaking copy-on-write. Owner: [Views and slicing](../issues/23-views-and-slicing.md).
3. **Kernel cache keyed on symbolic extents.** Field sizes change at every time step, and run-time scalars (`dt`, Butcher and ROCK coefficients) change at every stage. Neither may trigger a recompilation. Owner: [Kernel IR](../issues/22-kernel-ir.md), question left open in [Broadcasting design](../issues/13-broadcasting-design.md).
4. **Cheap reallocation at a new size every step, and buffer placement that avoids aliasing.** Pools behind the allocator are mandatory, and the allocator must stagger the start offsets of large buffers (ponio PR #115 lost up to 43% to page-aligned `mmap` arrays). Owner: [Buffer reuse and allocation](../issues/21-buffer-reuse-and-allocation.md), building on [Memory pools](../issues/20-memory-pools-research.md).
5. **Fusion of many-operand linear combinations with run-time scalars.** `ui = un + dt * sum a_ij kj` with up to 20 operands must give one kernel that reads each operand once. The pending window must also accept the in-place output of `f(t, y, dy)` without a copy when `dy` is uniquely held. Owner: covered in principle by [When the task graph is evaluated](../issues/08-evaluation-trigger.md); operand limits per kernel (GPU parameter space) go to [Kernel IR](../issues/22-kernel-ir.md); in-place reuse to ticket 21.
6. **`fixed<T, N...>` must cover what samurai does with `xtensor_fixed`.** That means vectors and small matrices, row and column views (`xt::col(jac, d)`), arithmetic usable in device code and in Kokkos kernels, a collapse rule for one component, and AoS storage of `tensor<fixed<T, N>>` with an optional component-major layout for GPUs. Owner: [Tensor data model](../issues/07-tensor-data-model.md) (decided in principle), details in [Kernel IR](../issues/22-kernel-ir.md).
7. **A path for user lambdas over fixed-size elements.** Flux functions, cell schemes, Jacobians and BCs are per-element lambdas. Either the Kokkos interop header is fast enough to be the main path (a lambda per interface over `fixed` values, atomics allowed), or tensorlib traces generic lambdas with symbolic `fixed` arguments into the IR. Owner: [Kernel IR](../issues/22-kernel-ir.md) and [Backend interface](../issues/10-backend-interface.md) (the interop header).
8. **Atomic scatter-add.** Flux schemes add contributions from interfaces to both neighbouring cells, and two interfaces can hit the same coarse cell. The IR needs a scatter-add output (atomic or coloured). Owner: [Kernel IR](../issues/22-kernel-ir.md).
9. **Reductions that do not go through host iteration.** ponio's `error_estimate` and `norm` iterate with `begin/end`; on a device tensor this would be a host read of the whole state. tensorlib must offer fused reductions (`max(abs(...))`, weighted RMS of an expression) so that ponio can specialise these two functions, and samurai's per-component max. Owner: [Kernel IR](../issues/22-kernel-ir.md) (reductions as nodes).
10. **Masks and bit-flag tags.** `uint8` tags with bitwise and/or, and masked updates. Owner: [Views and slicing](../issues/23-views-and-slicing.md) (non-affine access).
11. **Zero-copy export of a local buffer to PETSc.** samurai wraps field storage with `VecCreateSeqWithArray`; tensorlib must hand out the evaluated local buffer pointer the same way. Owner: [PETSc and Tpetra interop](../issues/17-petsc-tpetra-interop.md).
12. **Gather and scatter by interval lists for halo packing.** samurai's MPI exchanges pack and unpack interval runs into contiguous buffers. With a segmented gather kernel (requirement 1), packing stays on the device. The exchange itself stays in samurai. Owner: [Distribution kinds](../issues/18-distribution-kinds.md) and the fog "distribution hooks in the graph".
13. **64-bit signed indexing** for storage offsets. Owner: [Kernel IR](../issues/22-kernel-ir.md).
14. **O(1) `swap` and value copies that satisfy ponio's `state_t` concept.** COW gives both. Owner: [Tensor data model](../issues/07-tensor-data-model.md), [ADR 0001](../../../docs/adr/0001-value-semantics-with-copy-on-write.md).
15. **Reference workloads.** Add to the map's workload list: ponio `heat_bench` (`rk_44`, `rkc_202`, ROCK2/4, 10^6 cells), samurai `advection_2d` with adaptation, `burgers` SSP-RK3, the LBM Rayleigh-Taylor case, and samurai's `benchmark_fv_scheme`, `benchmark_update_fields` and `benchmark_detail_computation`. Owner: fog "Test and benchmark infrastructure".

## Conflicts with decisions already taken

1. **samurai meshes do not map to a partitioned tensor with a regular global index space.** [Tensor data model](../issues/07-tensor-data-model.md) and the glossary define a distribution as a split of a tensor's global index space. A samurai field has no global index space: each rank numbers its own cells across all levels in mesh order, the size changes at every adaptation, load balancing moves arbitrary sets of cells, and ghosts come from set intersections with each neighbour. Within tensorlib's current model, a samurai field is a *local* tensor on each rank, and samurai keeps its own communication. Ticket 18 should either accept that (and offer only the gather and scatter kernels of requirement 12), or add an irregular distribution described by index lists, like Tpetra `Map` with arbitrary global IDs or PetscSF. Nothing decided so far covers the second option.
2. **Ghosts are interleaved, not a band.** Ticket 07 says a distribution can declare a ghost width, with storage that includes the ghosts and an accessor for owned plus ghost cells, in the style of DMDA. samurai's ghosts sit among owned cells in one numbering, at every level. The ghost-width model does not apply to samurai at all.
3. **"One affine index map per leaf" does not cover samurai's access.** [Broadcasting design](../issues/13-broadcasting-design.md) fixed one affine map per kernel operand. samurai needs a map that is affine inside each interval but jumps between intervals (requirement 1). Either the IR gains segmented iteration spaces, or every samurai operator becomes a separate small kernel or an interop call, which is the overhead samurai has just removed by hand.
4. **User lambdas cannot enter the IR ([ADR 0003](../../../docs/adr/0003-runtime-backend-interface-on-lowered-kernels.md)).** Most samurai physics is in user lambdas over small arrays. Under ADR 0003 these run through the Kokkos interop header as non-fusible triggers, so tensorlib's fusion helps only the whole-field linear algebra around them (ponio stages, `u - dt * conv(u)`). Tracing generic lambdas with symbolic `fixed` arguments would keep the ADR (no user code in the IR, only what it records) but has to be decided in ticket 22.
5. **Collective triggers and `local_part()`.** Since samurai fields would be local tensors (conflict 1), the SPMD rules of [ADR 0002](../../../docs/adr/0002-implicit-pending-windows.md) do not apply to them, and global reductions (time step, norms) stay with the user's MPI calls. This is consistent with ADR 0002 but means tensorlib does not help samurai with distribution.
6. **Small pending windows.** samurai alternates whole-field expressions with interval loops that read the results, and each read is a trigger ([When the task graph is evaluated](../issues/08-evaluation-trigger.md)). Windows will hold a few nodes, so the fixed cost per evaluation (about 0.5 us measured in ticket 09) matters more than the fusion gain, except for ponio stages. This does not contradict the decision, but it argues for keeping evaluation overhead very low and for a mode where an interop kernel joins the window instead of flushing it.
7. **Raw pointers from `data()` are host pointers.** samurai's rewritten operators use `field.data()` in host loops. With a run-time memory space, `data()` on device memory is a trigger plus a transfer, and every write through it needs the copy-on-write uniqueness check. Porting those loops means rewriting them as tensorlib expressions over segmented views or as interop kernels. The decision is not wrong, but samurai's current style does not survive the move to GPUs unchanged.

No conflict found with [Minimum C++ standard and build system](../issues/14-cxx-standard-and-build.md): both libraries are C++20, CMake, conda-forge.
