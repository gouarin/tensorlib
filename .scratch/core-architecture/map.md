# Core architecture of tensorlib

Labels: wayfinder:map
Status: closed (2026-10-31). Destination reached: [spec.md](spec.md). [Rerun the fusion benchmark on an HPC node and a GPU](issues/19-rerun-fusion-benchmark-hpc-gpu.md) stays open as a later check, listed in the spec's open items.

## Destination

An architecture spec for the core of tensorlib, with decisions locked on the tensor data model, the task graph and loop fusion, broadcasting, the backend interface, the compile-time strategy, the surface exposed to bindings and the zero-copy interop hooks with PETSc and Tpetra. The spec is ready to be split into implementation tickets.

## Notes

- Domain: a C++ tensor library close to NumPy and the Array API standard, in the spirit of xtensor, running on Kokkos (SIMD, CPU threads, GPU) and aimed at distributed HPC machines. Performance on distributed machines comes first.
- Container kinds: fixed-shape, fixed-rank and dynamic-rank tensors, like `xtensor_fixed`, `xtensor` and `xarray`. See `CONTEXT.md`.
- The core defines its own backend interface. Kokkos is the main implementation, and a serial backend must stay possible.
- The data model carries the notion of a partitioned tensor from the start. The first milestone runs in shared memory only (CPU and one GPU).
- Code-generation families to explore: lighter templates, and a run-time graph compiled by a JIT. Precompiled generic kernels are ruled out.
- Platforms: Linux (GCC, Clang), macOS (Apple Clang), Windows (MSVC), NVIDIA, AMD and Intel GPUs.
- Reference workloads for every performance decision: samurai (`advection_2d` with adaptation, `burgers` SSP-RK3, the LBM Rayleigh-Taylor case, `benchmark_fv_scheme`, `benchmark_update_fields`, `benchmark_detail_computation`) and ponio (`heat_bench` with `rk_44`, `rkc_202`, ROCK2/4 on 10^6 cells); stencils on structured grids, fused element-wise expressions with several outputs (`c = a + b; d = a + 2*b`), reductions with broadcasting, dense and sparse linear algebra.
- Reference users: tensorlib must give optimal performance to the user's libraries [samurai](https://github.com/hpc-maths/samurai) (AMR and multiresolution) and [ponio](https://github.com/hpc-maths/ponio) (time integration). Their hot loops are acceptance workloads for every performance decision.
- Primary user: the C++ HPC developer writing simulation codes. Bindings drive the same core from Python, Julia and Rust; competing with JAX or Heat in Python is not a goal.
- Dependencies: `mdspan` in the core; Kokkos core, Kokkos Kernels and Kokkos-FFT through the Kokkos backend only; MPI behind a tensorlib communication interface (Kokkos Comm later).
- Reuse before building: the user does not want to reinvent the wheel. When a library is already very efficient in an HPC setting, say so, and prefer adopting, extending or depending on it over rewriting it.
- Code quality bar (user requirement, 2026-10-30): the code written from this spec must be extremely easy to read, concise, state of the art in modern C++, and extremely flexible. Every remaining decision weighs its effect on the code's readability and flexibility, and the spec states the resulting style rules before it is split into implementation tickets.
- License BSD-3. Code, docs, spec and tickets are written in English. Conversations with the user are in French.
- Skills for every session: `grilling` and `domain-modeling` for decisions, `research` for research tickets, `prototype` for prototype tickets, `humanizer` for any prose.

## Decisions so far

- [Assemble the architecture spec](issues/33-assemble-the-architecture-spec.md): the destination, [spec.md](spec.md), approved by the user; the default queue belongs to a context and device pair, and a segment table has one base column per distinct offset table.
- [Test and benchmark infrastructure](issues/32-test-and-benchmark-infrastructure.md): serial backend as the code-generation oracle and a test-only Python shim over the C ABI for array-api-tests and NumPy; bit-exact under `TL_FP=strict`, ulp bounds for transcendentals; a shrinking window generator; a threaded test communicator plus real MPICH and Open MPI; hosted CI matrix with sanitizers and compile-only GPUs, self-hosted GPU runners and computing-centre campaigns; a dedicated benchmark machine with significance-based alerts and same-job A/B; GoogleTest; compile-time budget with `-ftime-trace`.
- [C ABI and binding surface](issues/31-c-abi-and-binding-surface.md): one C ABI (`<tl/c.h>`, `tensorlib::c`) for Python, Julia and Rust, nanobind allowed only on top of it; one opaque value/view handle, no expressions; explicit `tl_context*` owning the pending window and the last error, movable between threads ([ADR 0012](../../docs/adr/0012-one-c-abi-with-explicit-contexts-and-generic-dispatch.md)); explicit core plus `tl_apply` over a generated catalogue; structured `tl_dtype` with `fixed` components; communicators from the Fortran handle; traced functions and external functions from bindings; C++ indexing semantics; `tl_status` codes; read-only DLPack export with scoped borrow.
- [Lowering of short segments](issues/30-lowering-of-short-segments.md): real samurai intervals have a median of 4 cells and ghosts between them; the generator bridges segments across gaps of up to 4 cells that `tl::segment_space` declares dead and accessible (49 % to 72-81 % of the span ceiling on advection); struct-of-arrays table with one shared base, LLVM's own tail, chunks balanced by cells, storage order kept; amends Kernel IR and `tl::segment_space` ([README](prototypes/30-short-segments/README.md)).
- [Coding style and extension points](issues/29-coding-style-and-extension-points.md): element types by traits, run-time registries for backends, resources and library ops, new operations as compositions, no CPOs or `tag_invoke`; closed IR plus a `call` to registered external functions; free Array API functions with designated-initializer options; public operations are one-line facades over a `.cpp` body ([ADR 0011](../../docs/adr/0011-thin-templates-over-an-erased-core-and-layered-extension-points.md)); `snake_case`, umbrella `<tl/tl.hpp>`; strict C++20 headers; `[[nodiscard]]` on `expr`, `tensor`, `view`; CI checks header rules, every public function has a compiled example.
- [Communication in the evaluation plan](issues/28-communication-in-the-evaluation-plan.md): ghosts exchanged only when a window reads them stale, sent right after an in-window writer, interior/boundary split above `TL_OVERLAP_MIN_CELLS`; one message per neighbour per exchange point, generated pack/unpack, one phase to every stencil neighbour; one non-blocking packed reduction per exchange point with the poison word, fixed tree under `TL_FP=strict`; four redistributions as non-blocking plan nodes; persistent patterns on `tl::communicator` driven by a progress thread ([ADR 0010](../../docs/adr/0010-persistent-communication-patterns-and-a-progress-thread.md)); plan hash in every message raises `tl::spmd_error`.
- [Prototype of the LLVM JIT on CPU](issues/27-llvm-jit-cpu-prototype.md): confirms the LLVM generator on CPU; flat kernels (ponio20, gather flux, canonical sum) run at the VM's bandwidth ceiling, bit-identical to g++; 3-7 ms cold compile, 0.06 ms from the disk cache; CPU ceiling defaults about 1 000 ops and 24 live lanes on NEON; canonical reductions reproducible and faster than Kokkos; gather beats atomic scatter 2-7x; segmented kernels at 60-82 % of a flat stencil ([README](prototypes/27-llvm-jit-cpu/README.md)).
- [Kernel IR](issues/22-kernel-ir.md): evaluation plan orders kernels and non-fusible nodes (library ops, interop, communication); a kernel is a per-element SSA program over a rectangular or segmented space, with no loops or tiles ([ADR 0009](../../docs/adr/0009-evaluation-plan-and-per-element-ssa-kernel-ir.md)); lane-typed `fixed` values with a component stride; Array API types plus f16/bf16 storage, explicit casts; built-in and traced combiners, scans apart; affine scatter-add turned into gathers, indirect ones atomic unless deterministic; several bodies selected per segment; 64-bit semantics with a 32-bit variant by capability; round-trip text form and incremental hash.
- [Code-generation strategy](issues/12-code-generation-strategy.md): one generator from the IR to LLVM IR, in-process LLVM required in the Kokkos backend, with a read-only kernel bundle and `TL_JIT=off` ([ADR 0008](../../docs/adr/0008-in-process-llvm-as-the-only-code-generator.md)); minimal cache key, everything else (extents, segments, scalars) as arguments; automatic plan cache, no explicit capture; every rank compiles, one writer per node; FMA allowed and reductions in a fixed order, reproducible at fixed rank count; Kokkos owns CPU threads, JIT emits `body(begin, end, args)`; two tunable kernel-size ceilings; decided on CPU evidence, GPU checked later.
- [Error reporting and debug mode](issues/24-error-reporting-and-debug-mode.md): every statement records a `tl::site`, kernels are named after the sites fused into them; checks (`sync`, `bounds`, `nan` from finite inputs, `uninit`, `scatter`, `leaks`, `detaches`, `reads`) set by `TL_DEBUG` or a collective `tl::debug_scope`, on the real backend; failed kernels and OOM poison their outputs, and the poison crosses ranks with ghost messages and reductions so every rank throws at the same read ([ADR 0007](../../docs/adr/0007-errors-poison-results-across-ranks.md)); host usage errors always thrown at once; amends PETSc interop and Buffer reuse.
- [Views and slicing](issues/23-views-and-slicing.md): `tl::view` is a reference type distinct from value tensors and the type of output parameters ([ADR 0006](../../docs/adr/0006-views-are-references-distinct-from-tensors.md)); NumPy/Array API slicing through `operator()`, out-of-bounds ranges are errors; partial writes on shared buffers detach in one fused pass; `tl::box` with offsets for stencils, ghosts read in global coordinates; masks are write-only targets, index views gather and scatter, `+=` accumulates duplicates; `tl::segment_space` for samurai intervals; slices restrict distributions without communication; `reshape` always returns a value.
- [Buffer reuse and allocation](issues/21-buffer-reuse-and-allocation.md): only an assignment target reuses its buffer, checked on the host at evaluation with a capacity rule; one queue-ordered `tl::memory_resource` per space, Umpire `ResourceAwarePool` by default and required by the Kokkos backend, user pools pluggable ([ADR 0005](../../docs/adr/0005-queue-ordered-memory-resources-with-umpire.md)); frees deferred in queue order; temporaries allocated per kernel boundary, arena later if needed; staggered host offsets; `resize` = `tl::empty`; OOM retried once then `tl::out_of_memory` at the trigger; no NUMA logic in v1.
- [Zero-copy interop with PETSc and Tpetra](issues/17-petsc-tpetra-interop.md): vectors and DMDA in v1, matrices opaque; scoped `borrow` (tensorlib owns) and `wrap` (PETSc/Tpetra owns) that evaluate, wait, keep copy-on-write and ghosts coherent; ghost band kept, so ghosted tensors are zero-copy as DMDA local vectors and go through an explicit `borrow_packed` for global vectors; DMDA built from or read into a distribution, cached on it; full sync by default, stream-ordered opt-in; `tl::petsc::mult` and `tl::tpetra::apply` as non-fusible window nodes; facts in [research/17](research/17-petsc-tpetra-apis.md).
- [Distribution kinds](issues/18-distribution-kinds.md): local, replicated and block over an n-d process grid (balanced or explicit sizes, block-cyclic later); immutable shared distribution, compatible when same ownership ranges on a congruent communicator (ghosts ignored); ghosts as width/stencil shape/periodicity per axis; ghost exchanges inserted automatically by the graph ([ADR 0004](../../docs/adr/0004-automatic-ghost-updates-in-the-graph.md)); empty local parts legal.
- [Reconcile the core with samurai and ponio](issues/26-reconcile-with-samurai-ponio.md): samurai fields are local tensors (samurai keeps mesh, balancing, MPI; tensorlib gives segmented gather/scatter); segmented iteration spaces in the IR (affine per segment, amends Broadcasting design); generic lambdas traced with `tl::apply` into the IR; interop kernels join the window instead of flushing it; requirements passed to Kernel IR, Views and slicing, Buffer reuse and PETSc interop.
- [Requirements from samurai and ponio](issues/25-samurai-ponio-requirements.md): samurai fields are flat per-rank arrays indexed by interval offsets that change every step, with no global index space, so they are local tensors to tensorlib; needs segmented iteration spaces in the IR, symbolic-extent kernel cache, cheap per-step reallocation, scatter-add, fused reductions, and a fast path for per-element user lambdas; ponio needs fused combinations of up to 20 stages with run-time coefficients, O(1) swap and in-place `f(t, y, dy)`.
- [Minimum C++ standard and build system](issues/14-cxx-standard-and-build.md): C++20 floor tied to Kokkos 5, C++23 only behind feature-test macros; public headers limited to a light std whitelist checked in CI with a compile-time budget; typed C++ exceptions, status codes at the C ABI, device errors at wait; CMake >= 3.25.2 with presets and exported targets, deps via find_package; Spack and conda-forge recipes.
- [Broadcasting design](issues/13-broadcasting-design.md): exact Array API rule, shapes checked at node build, in-place never reshapes; `broadcast_to` returns a read-only `tl::expr` (expand_dims stays a view); one affine index map per leaf (stride 0 only in the IR) shared with slices, transposes and shifts, aliasing by map comparison, flat loop when shapes match; `tensor<vec3> + vec3` and scalar-times-lanes, `as_components()` otherwise; partitioned operands must be aligned or replicated, never implicit communication.
- [Prototype of compile times for lighter templates](issues/11-compile-time-prototype.md): a graph-recording front-end (operators on type-erased `tl::expr`, nodes recorded by functions compiled once) compiles in 0.01-0.44 s against 1-127 s for xtensor (superlinear, 7.4 GB at 64 statements) and still runs faster; no expression templates for run-time-sized tensors; `fixed<T, N...>` evaluated eagerly and `constexpr`.
- [Backend interface](issues/10-backend-interface.md): run-time backend registry fed with kernels already lowered to an internal IR plus named library operations; queue-ordered allocate/free/copy, queues and events, memory spaces host/device/pinned/managed, declared capabilities for per-target lowering; missing library op is an error; Kokkos backend (1 device per rank, Umpire required since [Buffer reuse and allocation](issues/21-buffer-reuse-and-allocation.md), unmanaged Views) and a dependency-free serial interpreter as test oracle; Kokkos interop header for user kernels ([ADR 0003](../../docs/adr/0003-runtime-backend-interface-on-lowered-kernels.md)).
- [Memory pools for HPC tensors](issues/20-memory-pools-research.md): Kokkos has no usable pool (every View free fences); depend on Umpire (MIT, host/CUDA/HIP/SYCL, `QuickPool` then stream-aware `ResourceAwarePool`) behind the backend allocator, wrap buffers as unmanaged Views, offer CCCL/HIP native pools and RMM (CUDA only) as optional adapters; deferred frees and temporary planning decided in [Buffer reuse and allocation](issues/21-buffer-reuse-and-allocation.md).
- [Prototype of multi-output fusion](issues/09-multi-output-fusion-prototype.md): pending window validated (one kernel per window, beats two loops and xtensor, ~5 ns per recorded node, ~0.5 us per evaluation); fused kernels must be straight-line loops since a block interpreter costs 1.2x (DRAM) to 1.5x (cache) the hand-fused loop and does not map to GPUs; buffer reuse is mandatory (fresh allocations cost 2x to 6.6x); measured with Google Benchmark on a VM, GPU and real-node numbers still to come.

- [When the task graph is evaluated](issues/08-evaluation-trigger.md): implicit pending window per host thread, evaluated as a whole by a trigger (read/export, `tl::eval`, non-fusible consumer, deterministic limits); collective triggers under SPMD; results as if immediate; `auto t = a*b` is a never-stored `tl::expr`; asynchronous launch ([ADR 0002](../../docs/adr/0002-implicit-pending-windows.md)).

- [Tensor data model](issues/07-tensor-data-model.md): one tensor type carrying a distribution (local by default, mixing is an error except replicated operands); value semantics with copy-on-write ([ADR 0001](../../docs/adr/0001-value-semantics-with-copy-on-write.md)); `tensor<T, Rank = dynamic>` plus inline `fixed<T, N...>` usable as element type; static dtype in C++, erased `any_tensor` at the edge; memory space and layout are run-time attributes.

- [Build, extend or adopt](issues/16-build-extend-or-adopt.md): build only the C++ tensor layer as a new project with an xtensor-inspired API; depend on mdspan, Kokkos (Kernels, FFT) via the backend and MPI behind a comm interface; interoperate with PETSc and Tpetra; C++ HPC developers first.
- [State of the art of lazy, fused tensor libraries](issues/01-lazy-fusion-state-of-the-art.md): templates (xtensor, Eigen, Blaze) fuse only within one assignment; multi-output fusion needs a run-time graph that sees all outputs before choosing kernels (XLA, MLX compile, ArrayFire eval(c, d), Halide compute_with).
- [Broadcasting semantics and edge cases](issues/05-broadcasting-semantics.md): exact NumPy/Array API rule ("is 1", so 1 vs 0 gives 0); broadcasting as an index map inside fused kernels, not stride-0 views; in-place never reshapes the target and aliased reads force a copy; partitioned tensors broadcast on the global shape.
- [Existing HPC libraries that cover part of tensorlib](issues/15-existing-hpc-libraries.md): no library covers the full scope; Legate/cuPyNumeric (closest) archived in 2026; build only the C++ tensor layer on Kokkos, depend on Kokkos Kernels, Kokkos-FFT, mdspan, and interoperate with PETSc and Trilinos/Tpetra instead of a PETSc-like layer.
- [C++ standard support across target toolchains](issues/04-toolchain-support-matrix.md): Kokkos 5 sets a C++20 floor (GCC 10.4, Clang 14, MSVC 19.30, NVCC 12.2, ROCm 6.2, CMake 3.22); C++23, modules and std::mdspan are not portable yet, so use Kokkos::mdspan and gate C++23 features behind feature-test macros.
- [Feasibility of JIT compilation with Kokkos](issues/03-jit-with-kokkos.md): feasible on CPU, CUDA, HIP and SYCL, but beside Kokkos rather than through it: Kokkos owns streams and the thread pool (storage later moved to the backend allocator by [Backend interface](issues/10-backend-interface.md)); an in-process LLVM lowers one internal IR to native kernels, with a memory-then-disk kernel cache.
- [Techniques to cut compile times of template-heavy libraries](issues/02-compile-time-techniques.md): modules are not an option (nvcc, hipcc, icpx, Apple Clang), so the core ships as plain headers; cut compile time with no heavy std headers in core headers, shallow templates, an early type-erased boundary, explicit instantiation only on closed type sets, and compile-time benchmarks in CI.
- [Binding surfaces for a lazy tensor library](issues/06-binding-surfaces.md): small versioned C ABI over an opaque, refcounted, possibly unevaluated dynamic-rank handle, DLPack at the edge for evaluated single-device buffers; partitioned tensors gathered or exported per local part.

## Not yet specified

- Communication on the device: a device path for large partial reductions across ranks (host staging in v1), stream-triggered communication (MPIX streams, NCCL, RCCL, Kokkos Comm) and pack fusion into writers, to weigh once GPU numbers exist ([Communication in the evaluation plan](issues/28-communication-in-the-evaluation-plan.md)).

## Out of scope

- Storing samurai's ghost cells apart from its intervals, which would close the last 1.5x between segmented and flat kernels: a samurai change ([Lowering of short segments](issues/30-lowering-of-short-segments.md)).
- Implementing the MPI backend and multi-GPU execution: the spec only fixes their hooks.
- Implementing the bindings for Python, Julia and Rust.
- Designing and implementing a PETSc-like linear algebra layer: tensorlib interoperates with PETSc and Tpetra instead ([Build, extend or adopt](issues/16-build-extend-or-adopt.md)).
- Distributed FFT: Kokkos-FFT is local only, and a distributed FFT is a separate effort.
- A Python-first distributed NumPy competing with JAX or Heat.
